# GRAN バックエンド/フロントエンドの OOP リファクタリング（FEAT-001〜005）

10 コミット・80 ファイル・約 +5987/-1922 行。entries をパイロットに、auth / tournaments / teams / data / notifications の各 feature をリッチドメインモデル（Entity / 値オブジェクト / Domain Service）、Repository インターフェース + Sqlite 実装、トランザクション境界を握る Application Service、`'use server'` を薄いアダプタへ縮退させる構成へ作り替えた。手動 DI のコンポジションルート（`src/server/container.ts`）が全サービスを配線し、共有ドメイン基盤（`src/domain/errors.ts`・`src/domain/GranLevel.ts`・`src/lib/unitOfWork.ts`）を新設。フロントは状態→ラベルの単一情報源（`statusLabels.ts` + `StatusBadge.tsx`）へ重複を集約。外部契約（Server Action の名前/引数/戻り値形、ユーザー可視文言、DB スキーマ）は保存するという強い制約のもとでの内部構造変更。

## High-level view

ビヘイビア保存は成立している。`src/lib/db.ts` は diff ゼロでスキーマ無変更。entries と auth の新アダプタ + `toActionResult` を base ブランチの旧 `actions.ts` と突き合わせた結果、Server Action の export 名・シグネチャ・結果型・ユーザー可視文言はすべて 1 バイト一致。境界を越える読み取りは `EntrySummary` / `EntryMemberView` という plain interface の DTO で、Entity クラス（`Entry` / `Tournament` / `GranLevel`）はサーバ内部に留まる。

振る舞いの分岐順序も忠実に移植されている。submit の 4 段構造（同日確認・事前満員は UoW 外の早期復帰、重複再チェック・定員再チェック・挿入は UoW 内）、waitlist の requiresTeam ネスト（SINGLES は代表者文言に到達しない）、login の順序（存在→ロック→停止→照合→失敗記録）、キャンセル料アルゴリズム（Math.round・当日 0 起点・50% は Math.floor）、定員再チェック（`confirmedCount >= capacity`）、確定数カウント（CONFIRMED + ATTENDED）が旧実装と一致する。

design-review の持ち越し A/B/C はクローズ済み。A（権限判定を 4 ユースケースすべて Application Service へ集約）は `EntryApplicationService` のコードで確認。B（規約 §2 のディレクトリ命名注記）と C（fetch サイト・CancelFeePolicy 生成箇所のドキュメント記述）は FEAT-001 の設計ドキュメント編集と FEAT-005 の規約（Antigravity-instructions.md）編集として実施済み。

共有ドメイン基盤の `GranLevel` は旧 `granLevelToTier` / `granLevelToClassLabel` を VO に吸収したが、コンストラクタに 100〜999 の範囲検証を新設した。旧関数は無検証だったため厳密化だが、`gran_level` カラムの `CHECK (BETWEEN 100 AND 999)` 制約により永続値は常に範囲内で、throw 分岐は実行時到達不能。防御的追加であり回帰ではない。

検証ゲートは記録済みの証跡で green。FEAT-001/002/005 は tsc=0 / npm test green（43→88→98 件）/ build 成功を記録。FEAT-004 の唯一の非 green は、ユーザー稼働プロセスが WAL ロックを握ることによる外部 SQLite ロック（文書化済み caveat）と、全スイート負荷下での `ranking.test.ts` Property 6 のタイムアウト（単体実行では green のフレーク）であり、コード起因の回帰ではない。

### Server Action 外部契約と文言の 1 バイト保存

entries の新アダプタ（`src/features/entries/server/actions.ts`）と純マッパ `toActionResult.ts` を base ブランチの旧 `actions.ts` と突き合わせた。export された 5 アクション（submit / bulk / waitlist / cancel / updateMembers）と `getMyEntriesAction` の名前・シグネチャ、`EntryActionResult` / `MyEntriesResult` の形は不変。文言は旧実装と一致する。例として pre-full は `この大会は満員です。キャンセル待ちへご登録ください。`、TOCTOU は `直前に満員となりました。キャンセル待ちへご登録ください。` と別経路・別文言のまま。auth も同様で、login の汎用エラー（`ログインID またはパスワードが正しくありません。`）、ロック案内、停止案内、register のメール重複文言が旧 `actions.ts` と一致する。

権限文言・NotFound 文言は `PermissionDeniedError.context`（5 種）・`NotFoundError.context`（entry/user/tournament/team）経由で `PERMISSION_MESSAGE` / `NOT_FOUND_MESSAGE` にマップされ、旧アダプタの早期 return 文言を再現する。DB・不明例外は操作別の汎用 catch 文言（`GENERIC_CATCH_MESSAGE`）へ落ちる。

### submit の UoW 内外分割と TOCTOU 再チェック

旧 `createConfirmedEntry` は `BEGIN IMMEDIATE` 内で hasActiveEntry + 定員チェック + 挿入を行っていた。新 `EntryApplicationService.submit` は、前提・権限・メンバー構成・同日重複・事前満員を `uow.run` の外に置き、重複「再」チェック（`DuplicateEntryError`）・定員「再」チェック（`!canAcceptEntry` → `EntryFullError`）・挿入を `uow.run` の中に置く。`canAcceptEntry(confirmedCount)` は `confirmedCount < capacity` を返すので `!canAcceptEntry` = `confirmedCount >= capacity` となり、旧 `confirmed.c >= capacity` と一致する。`SqliteEntryRepository.countConfirmed` は `status IN ('CONFIRMED','ATTENDED')` を数え、旧 `confirmed_count` サブクエリと同一集合。事前満員判定も `tournament.remaining(countConfirmed) <= 0`（= `Math.max(0, capacity - confirmed) <= 0`）で旧 `calcRemaining` と一致する。

### 権限判定の Application Service 集約（design-review Finding A）

submit / submitWaitlist / cancel / updateMembers の権限判定はすべて `EntryApplicationService` に存在する。submit はフラットに `requiresLeader` → `requiresTeam`（teamId 必須・所有権）を前段検証。submitWaitlist は代表者判定を `requiresTeam` ブロックの内側にのみ置き、SINGLES では `leaderOnlyWaitlist` / `teamOwnership` に到達しない旧ネスト構造を保存する。cancel / updateMembers は共通 `assertEntryManagePermission`（本人 / チーム代表 / 管理者）で、旧アダプタの分岐（`entry.userId === user.id` → `team.leaderUserId === user.id` → `user.isAdmin`）を文言ごと移設している。アダプタ層は session + Zod + 配線 + 例外→Result + revalidate + COMMIT 後通知のみで、権限判定を持たない。

### 境界を越える DTO とエンティティの非越境

書き込み系 `EntryMember` クラスと読み取り DTO `EntryMemberView` を別物として一意化したのがこの非越境の要。`EntrySummary.members` の要素型は `EntryMemberView`（plain interface）で、`entries/server/actions.ts` の import は `EntrySummary` / `MemberType` の型のみ。tournaments も `TournamentWithStats` のプレーンフィールド（`remaining: number` / `capacityStatus`）を維持し、`Tournament` エンティティはリポジトリ/クエリサービス内部に留まる。

### GranLevel VO の範囲バリデーション（confirmed・非ブロッキング）

`src/domain/GranLevel.ts` のコンストラクタは `!Number.isInteger(value) || value < 100 || value > 999` で `RangeError` を投げる。一方、旧 `granLevelToTier` / `granLevelToClassLabel`（`auth/utils/classLabel.ts`）は無検証で、0 や範囲外でも `>= 850…` の連鎖比較の結果 `DE` / `DE級` を返していた。委譲ラッパ・`RankingService.rankUsers` / `buildSelfRankSummary`・`LevelDistributionService.buildDistribution`・`AppShell.tsx` の全呼び出しが、新たに範囲外入力で throw し得る。

ただし `src/lib/db.ts` の users テーブルは `gran_level INTEGER NOT NULL DEFAULT 100 CHECK (gran_level BETWEEN 100 AND 999)` で、永続値は常に 100〜999。`estimateInitialGranLevel` も 100〜999 にクランプした値のみ生成する。したがって throw 分岐は実行時に到達不能で、プロパティテスト `tier.test.ts` も 100〜999 の `granLevelArb` で検証している。旧コードより厳密な防御的バリデーションの追加に留まり、回帰ではない。

`buildSelfRankSummary` は `isCalibrated === false` でも `new GranLevel(viewer.granLevel)` を無条件に構築するが、これは旧 `buildSelfRankSummary` が `granLevelToTier(viewer.granLevel)` を無条件に呼んでいた構造と同一であり、スキーマ不変条件（100 以上）のもとで安全。

### cancel のステータス検証順序と失敗モードの微差（confirmed・非ブロッキング）

旧 cancel は `entry.status !== "CONFIRMED"` 検証を tournament 取得より前に行っていたが、新 `cancel` は設計 §6.2.2 に従い findById → 権限 → tournament 取得 → `entry.cancel()`（内部で status 検証）の順。『未確定エントリー かつ 大会レコードも存在しない』という稀ケースでのみ、返る文言が旧『このエントリーはキャンセルできません。』から新『大会が見つかりません。』へ変わる。FEAT-002 findings に記録済みの意図的判断で、設計書を authoritative とした結果。

同様に register は旧 try 外の `emailExists` 検査が `AuthApplicationService.register`（アダプタ try 内）へ移動したため、`emailExists` 中の DB 例外が伝播から `登録処理でエラーが発生しました。…` へ変化する。fail-closed 方向で、ユーザー可視文言は既存の汎用 catch と一致。

### キャンセル料アルゴリズムの保存

`CancelFeePolicy.calculate` は旧 `calculateCancelFee` を 1:1 で移設。`toDateOnly`（`/` と `-` 両許容）、`Math.round(diffMs / 86400000)`（当日 0 起点）、`>= 8 → 0%` / `>= 3 → 50% (Math.floor(fee*0.5))` / それ以外 `100%` の境界、`adminStatus` の初期値が一致する。規約 §5.1 サンプルの `Math.ceil` / `daysBefore>=3 && <=7` は非規範として FEAT-005 で注記され、実装は採用していない。残置ラッパ `utils/cancelFee.ts` は `CancelFeePolicy` へ委譲し、CancelEntryModal 等のクライアント呼び出しを壊さない。

### コンポジションルートと最小依存インターフェース

`container.ts` が唯一の配線点として各 `create*Service` を公開。entries は自 feature の `dependencies.ts` に最小 interface（`TournamentView` / `TeamView` / `UserView` / `NotificationService`）を定義し、container が各 feature の本物の Sqlite リポジトリ/サービス実装へ委譲してこれを満たす。注意点: FEAT-002 時点のスタブ（既存公開関数の上の薄い配線）は後続 FEAT で本物の実装へ差し替え済み（例: notifications は `RealNotificationService` + `SqliteNotificationRepository`）なので、スタブ残存による二重経路は無い。
