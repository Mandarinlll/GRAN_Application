# 機能要件詳細定義書（1. ユーザー向け機能）

## 1. アカウント・認証
### 1.1 新規登録（LINE連携 / ローカル手動）

* **概要**: LINE連携による登録、またはメールアドレス登録を行う。

* **処理詳細**:
  * 基本的にユーザID(`user_id`)をユーザは認識しない。
  * 基本的にLINE・メール以外の登録方法は用意しない（連絡がつく必要が必ずあるので）
  * 権限：「管理者」「運営者」「代表者」「ユーザ」の４分類に分かれる。
  * 代表者：各チーム2名まで割り当て可能。（チーム作成者（代表者）がもう一人をチームに招待したユーザの中から指定可能（権限の付与））

  1. **LINE新規登録**: LIFF起動時、`line_user_id` を取得。システム側で `user_id`（ユーザID）を自動採番。
    - `user_id`：6桁の数字（000001など）
      - 000100以下：管理者や運営者
      - 000101以上：代表者・ユーザ
    - ログインには基本的に(`line_user_id`)を利用。（LINEの二段階認証を活用）

  2. **メールアドレス新規登録**
    * メールアドレス(`mail_user_id`)を登録後、(`user_id`)が自動採番。
      * メールでのログインの場合、入力したアドレスに確認メールを送る（二段階認証）

  3. **登録項目**
    - パスワード（8桁以上・英数字）
    - 氏名（本名）
    - フリガナ
    - ニックネーム※1
    - ユーザーアイコン画像URL※1
    - 性別（男・女の2択）
    - 生年月日
    - 電話番号
    - もっともよく出場する階級（A～E）※2
    - GRANレベル※2
      * ※1：外部に公開する用途での設定の為、個人情報が含まれるものを設定することは避けるようにユーザに案内
      * ※2：アカウント登録時に自己申告。
          この申告をもとに管理者・運営者で一人ずつレベルを決定していく。
    
  4. **GRANレベル初期値**: 新規登録時は上記登録項目をもとに手作業で査定
    - 未査定アカウントにはフラグ `is_level_calibrated: false`を付与。
    - 査定済アカウントにはフラグ `is_level_calibrated: true`を付与。
  - 査定基準：
    - A級：999~800
    - B級：799~600
    - C級：599~400
    - D級：399~200
    - E級・未出場：199以下


### 1.2 ログイン・ログアウト

* **概要**: LIFF自動認証またはログインID・パスワードによる認証。

* **処理詳細**:
  * **LIFFログイン**
    - LINEアプリ内からアクセスされた場合、`line_user_id` で照合し自動ログイン。
    - アプリからのログインの場合、初回ログイン以降はログイン状態を保持。ログアウト状態でのログインは
  * **メールアドレスログイン**: `mail_user_id` とパスワードで認証。


### 1.3 セッション管理方式

* **概要**：LINE/LIFF連携ログインおよび手動ローカルログイン（ID/PW）の2系統に対応し、高いセキュリティとモバイルでの利便性（再ログイン不要なUX）を両立するため、**JWT（JSON Web Token）＋ HttpOnly Cookie によるハイブリッド認証方式**を採用

  1. **トークン仕様および有効期限**

  | トークン種別 | 格納場所 | 有効期限 | 役割・検証方式 |
  | --- | --- | --- | --- |
  | **Access Token** | HttpOnly Cookie | **15分 〜 1時間** | API通信時の認可。サーバー側は署名検証のみでユーザーID・権限（ロール/管理者フラグ）を判定する。 |
  | **Refresh Token** | HttpOnly Cookie / DB | **30日間** | Access Token 期限切れ時の自動再発行用。DB（またはAuth基盤）側で失効状態を照合・管理する |

  2. **Cookie属性設定**: `HttpOnly = true`, `Secure = true`, `SameSite = Lax` を必須とし、JavaScriptからの直接アクセス（XSS攻撃）およびCSRF攻撃を防止する

* **認証フローおよびセッション維持**

  1. **ログイン時**:
    * **LINE（LIFF）認証**: LINE IDトークンを検証後、一意のユーザーを特定・自動サインインし、トークンペアを発行してCookieへセットする。
    * **ローカル認証**: ログインIDとパスワード照合成功後、同様にトークンペアを発行してCookieへセットする。

  2. **通常通信時**:
    * リクエスト時に自動付与される Cookie 内の Access Token を検証し、高速にアクセス権限を判定する。

  3. **バックグラウンド更新（サイレントリフレッシュ）**:
    * Access Token の期限が切れた場合、フロントエンドまたはAPIミドルウェアが Refresh Token を用いて自動で Access Token を再生成・更新する。

* **セッション無効化・セキュリティ制御**

  1. **ログアウト**:
    * クライアントの Cookie をクリアし、DB上の Refresh Token を失効（Revoke）処理する。

  2. **アカウント強制停止（BAN）/ パスワード変更時**:
    * DB側の該当ユーザーの Refresh Token を即時無効化する。
    * Access Token は短寿命（15分〜1時間）のため、最大でも有効期限切れのタイミングで完全遮断される。


### 1.4 アカウントロック
    ※LINE自動ログイン（LIFF）時はLINE側の認証基盤に準拠するため、本システムのパスワード照合失敗によるロック処理は発生しない。

* **ロック条件および解除仕様**

| 項目 | 仕様・閾値 | 詳細・動作 |
| --- | --- | --- |
| **連続失敗許容回数** | **10回** | 同一 `login_id` に対して連続して5回パスワード照合に失敗した場合にロックを発動する。|
| **ロック** | **永久** | 10回目の失敗後、半永久的に正しいパスワードが入力されても認証を拒否（アカウントロック状態）とする。 |
| **管理者による手動解除** | 管理者画面（A-04 / ユーザー管理） | ユーザーからの問い合わせに基づき、管理者が手動で即時ロック解除可能とする。|
| **失敗カウントリセット条件** | 認証成功時 | ロック未到達（1〜9回失敗）の状態で正しいパスワードによりログインが成功した時点で、失敗カウントを `0` にリセットする。 |

* **エラーハンドリング・セキュリティ配慮**

  1. **アカウント存在有無の隠蔽（ユーザー列挙防止）**:
    * 存在しない `login_id` が入力された場合でも、存在する `login_id` でパスワードを間違えた場合と同じ汎用エラーメッセージを返却する。
    * メッセージ例: `「ログインIDまたはパスワードが正しくありません。」`

  2. **ロック発生時の画面表示**:
    * ロック発動時およびロック中のアクセス時は、セキュリティを担保しつつ試行停止を促すメッセージを表示する。
    * メッセージ例: `「パスワードの入力試行回数が上限を超えました。安全のためアカウントをロックしています。管理者へお問い合わせください。」`


* **DB定義への反映項目（`users` テーブル拡張）**

アカウントロックの状態管理のため、`users` テーブルに以下の管理カラムを追加保持する。

| 物理名 | データ型 | NULL | 初期値 | 役割・説明 |
| --- | --- | --- | --- | --- |
| `failed_login_attempts` | `SMALLINT` | NO | `0` | 連続ログイン失敗回数（成功時に0リセット） |
| `locked_until` | `TIMESTAMPTZ` | YES | `NULL` | アカウントロック解除予定日時（NULLまたは過去日時なら正常稼働） |

```sql
-- users テーブルへのアカウントロック用カラム追加SQL
ALTER TABLE users 
ADD COLUMN failed_login_attempts SMALLINT NOT NULL DEFAULT 0,
ADD COLUMN locked_until TIMESTAMPTZ DEFAULT NULL;

```

### 1.3 プロフィール管理・閲覧

* **概要**: 自身のプロフィール編集および他ユーザーの公開プロフィール閲覧。

* **処理詳細**:
  * **マイプロフィール編集**: 氏名、フリガナ、電話番号、アイコン画像、ニックネーム、パスワード、LINE ID（`line_user_id`）の変更
  * **公開プロフィール**: 他ユーザーからは「ニックネーム」「アイコン画像」「GRANレベル（3桁数値）」「成績」のみが閲覧可能。
  * **免責表示**: 公開範囲設定は撤廃されているため、「ニックネームに個人情報を含めないこと」を画面上に明記。


* **ストレージ選定およびバケット構成**
本アプリはデータベースおよびバックエンド基盤に Supabase を採用するため、画像ストレージとして **Supabase Storage**（内部基盤: AWS S3 + CDN）を利用する。

  1. **バケット設計**:
  2. **バケット名**: `avatars`（パブリックバケットとして公開）
  3. **RLS（Row Level Security）/ アクセス制御**:
  4. **閲覧（SELECT）**: 全員可（認証不要・公開URLアクセス可能）
  5. **アップロード（INSERT / UPDATE）**: 認証済みユーザー本人のみ（自身の `user_id` または自身が代表を務める `team_id` パス配下のみ許可）
  6. **削除（DELETE）**: 認証済みユーザー本人のみ、または管理者（`is_admin = true`）

* **ファイル制限およびバリデーション仕様**

| 項目 | 仕様・制限値 | 詳細・エラーハンドリング |
| --- | --- | --- |
| **許可する拡張子** | `.jpg`, `.jpeg`, `.png`, `.heic` | フロントエンドおよびストレージ側の MIME Type 判定（`image/jpeg`, `image/png`, `image/heic`）で検証。SVGやGIF等はXSS・容量負荷防止のため拒否。 |
| **ファイル容量上限** | **最大 5MB** | アップロード時のクライアント側事前チェックおよび Supabase Storage の `file_size_limit`（5MB）で二重制限。上限超過時は `「画像サイズは5MB以下にしてください」` を表示。 |
| **推奨解像度・アスペクト比** | **1:1（正方形） / 512×512 px** | クライアント側（UI）で円形／角丸正方形プレビューを行い、可能であればアップロード前にクライアント側でリサイズ・圧縮を実施。|

* **保存ディレクトリ構造・オブジェクト命名規則**
古い画像のキャッシュ残りやファイル名重複による上書き事故を防ぐため、オブジェクトキーに UUID またはタイムスタンプを付与する。

```text
avatars/
├── users/
│   └── {user_id}/
│       └── avatar_{timestamp}.webp   # ユーザーアイコン画像
└── teams/
    └── {team_id}/
        └── avatar_{timestamp}.webp   # チームアイコン画像
```

* **DB格納仕様**:
* `users.avatar_url` および `teams.avatar_url` には、CDN経由の公開完全URL（例: `https://<project-ref>.supabase.co/storage/v1/object/public/avatars/users/...`）を格納する。
* 画像差し替え時は、DBのURL更新と同時にストレージ上の旧画像ファイルをバックグラウンドで物理削除（クリーンアップ）する。
* 退会機能は実装予定なし

## 2. 大会・スケジュール
### 2.1 大会一覧・受付表示

* **概要**: 開催予定大会の一覧表示（カード形式・カレンダー形式）および空き枠のリアルタイム表示。

* **処理詳細**:
  1. **一覧表示**: 日程、大会名、種目（男子団体/女子団体/ミックス団体/シングルス/ダブルス）、階級、会場、定員・現在の残り数を表示。
  2. 大会情報の構成
     - 日程
     - 大会名（イベント名）
     - 種目
     - 階級
     - 会場
     - 定員・現在の申し込み数（残り枠数）
     - エントリー費用
     - 開始時間（集合時間）
     - 景品
     - 備考

  3. **空き枠判定**: `tournaments.capacity`（募集枠数）と `entries`（確定数 `status: CONFIRMED`）の差分からリアルタイムに算出。

  4. **複数選択申込**: 複数の大会を選択して一括申込画面へ進む操作に対応。
  5. **一覧の初期ソート順**：開催日の降順（細心の大会が一番上に表示される）
  6. **過去大会の表示設定**：デフォルトでは非表示。表示ボタン操作で過去の大会も閲覧可能。
  7. **エントリー数の閾値**：エントリー可能枠の75%以上で「残りわずか」と表示。（黄色バッジ表示など）


### 2.2 大会詳細・要項確認

* **概要**: 大会一覧から詳細を確認可能。

* **処理詳細**:
  1. 大会要項画像をカード上部に表示。中段以下に詳細情報を表示。（大会情報の構成）試合前日の0:00にドロー表をさらに下部に公開。
  2. 現在のエントリー済みチームのみ表示（エントリー者は表示しない）

* 枠の空き状況に応じ「エントリー申込」または「キャンセル待ち申込」ボタンを表示。


### 2.3 カード形式表示、カレンダー表示

* **概要**: 大会日程のカード形式表示とカレンダー形式表示

* **処理詳細**:
* 表示形式を二つにする理由
  - カード形式：新着大会をより目立たせたいため、レシピ共有アプリの「クラシル」のホーム画面をイメージ。（実際にホーム画面もこの想定）
  - カレンダー形式：開催予定の大会を一覧で全て確認できるようにするための機能。
* 本アプリのホーム画面はカード形式表示を採用する予定の為、ユーザにとってはエントリーのメイン動線となる。
* ２つの表示形式はタブで切り替え可能


### 2.4 マイスケジュール

* **概要**: 自身または所属チームがエントリー中の大会・参加履歴の一覧表示。


* **処理詳細**:
* 「自分（ユーザ個人）」と「チーム」としてのエントリーはそれぞれタブで分けて表示
* 「エントリー中（確定）」「キャンセル待ち」「過去の参加履歴」などの、大会の属性はソートで絞り込み機能を採用

* 該当大会を選択することで、エントリー詳細（メンバー構成変更、キャンセル申請）へ遷移。

## 3. エントリー・申込管理
### 3.1 大会申込（種目別制御）

* **概要**: 種目に応じたエントリー申込処理。

* **処理詳細**:
* **シングルス**: ログインユーザー個人でエントリー。
* **団体戦・ダブルス**: 代表者のみ申込可能。（そのユーザが代表者かどうかを判定）
  - ダブルスは2名
  - 団体戦は4~6人（大会によって指定があるので、その都度指定）

* **メンバー指定**: 構成メンバーを以下の3種から選択して登録：
  1. **チーム内**: チーム内ユーザーを検索して指定（`user_id` 紐付け）。
  2. **チーム外**: 氏名を入力して検索（`guest_name`）。
  3. **ゲスト・未定枠**: 氏名を直接入力するか、後日登録として保留（`is_pending: true`）。
     - ゲスト・未定枠での登録後、その枠で実際に参加する本人がアプリに登録した場合、
     チームの代表者がそれらの枠を割り当てられるようにする。

* **完了通知**: エントリー完了後アプリから通知
* **重複排除**：同日に別会場・別チームで重複エントリーが無いようにする。
利用者のエントリー大会テーブルを参照して、既にエントリーがある日程のエントリーをする際は注意画面を表示。
承認後にエントリーができるようにする。また、他チームでの重複出場も防ぐ。


### 3.2 参加メンバー更新

* **概要**: エントリー後の「未定枠」の正式決定やメンバー差し替え。

* **処理詳細**:
* エントリー詳細画面、または大会10日前に届く通知から更新。
* 代表者・管理者の２権限で更新可能。
* メンバー変更が可能な最終期限は大会開催日の3日前（00:00:00）。それ以降の変更は原則不可能。
  * 上記の期間を過ぎて、メンバーが変更になった場合は、管理者へ通知
  * ただし、体調不良やその他妥当性のある理由でメンバーの変更が必要となるケースは、
  可能な限り、近いGRANレベルでの人員補充を努力義務として定義する。


### 3.3 キャンセル待ち・繰り上がり承諾

* **概要**: 満員大会へのキャンセル待ち登録と空き枠発生時の繰り上がり処理。

* **処理詳細**:
* 定員到達時、自動でキャンセル待ちキュー（`waitlists.queue_number` 連番）に登録。
* 先行確定者のキャンセルにより空きが発生した場合、最上位の待機者（団体戦の場合代表者）へ「繰り上がり案内LINE（ディープリンク付き）」を自動送信。
* ユーザーはリンク先（U-22画面）から期限内に承諾ボタンを押下することでエントリー確定に昇格。
* 繰り上がり承諾の有効期限：通知送信から24時間
  
* **処理のトリガー構成**
  - 定期実行バッチ（Cron: 1〜5分間隔） : 承諾期限を過ぎた案内（OFFERED）を検知し、ステータスを EXPIRED（期限切れ）に更新。
  - ユーザーの辞退操作（即時） : 画面（U-22）で辞退が選択された際に、ステータスを DECLINED（辞退）へ更新。
  - 共通処理の実行 : 上記のいずれかが発生した大会に対して、同一の「次点者繰り上がりロジック」を呼び出す。

* **次点者繰り上がりの処理フロー**
  - 次点者抽出（排他制御） : 該当大会の waitlists から、待機中（WAITING）かつ順番（queue_number）が最上位のレコードをロック取得。
  - ステータス・期限更新 : ステータスを OFFERED に変更し、開催日までの残日数に応じた承諾期限（accept_deadline）を設定。


### 3.4 キャンセル申請

* **概要**: 開催日までの日数に応じたキャンセル料率の自動判定と申請処理。

* **処理詳細**:
* **開催8日前まで**: 無料キャンセル。即時枠解放（`status: CANCELLED`）、キャンセル待ち繰り上がりトリガー起動、ユーザーへ完了通知。
* **開催7日前〜3日前**: キャンセル料50%発生。枠解放＋`cancellations` レコード作成（`fee_rate: 50`）＋管理者通知＋ユーザーへ案内通知。
* **開催2日前〜当日**: キャンセル料100%発生。枠解放＋`cancellations` レコード作成（`fee_rate: 100`）＋管理者通知＋ユーザーへ案内通知。

* ※アプリ内での即時オンライン決済機能は不要（管理画面での請求・振込確認運用）。
* 日数計算の基準時刻：開催日当日の00:00を起点とした日数計算

## 4. チーム管理
### 4.1 チーム作成・編集

* **概要**: 団体戦・ダブルスの母体となるチーム情報の登録・更新。
  * 各チームのテーブルに「創設者」という属性を持たせ、2名いる代表者の中での区別を図る

* **処理詳細**:
* **1ユーザー1代表制約**: 1つのアカウントは最大1チームのみ代表者（チーム作成者）になれる（DB `leader_user_id UNIQUE` 制約）。
  * 代表者は各チームに2名まで登録可能

* **設定項目**: チーム名、チームアイコン画像URL。

* **チームプロフィール**: チーム名、チームアイコン、代表者（ニックネーム）名、所属メンバー（ニックネーム）一覧、獲得ポイントを全体公開。

* 代表者の権限付与や移譲（他の所属メンバーへの代表権移譲）機能：創設者のみ可能
  * 創設者より指名を受けた代表者は代表者権限を付与したり移譲する権限はない
* チーム解散（削除）時は過去エントリー・戦績データを保持しない


### 4.2 メンバー管理

* **概要**: チームへのメンバー追加・招待・除名。

* **処理詳細**:
* 一般メンバーは複数のチームに重複して所属可能。

* メンバーの追加・除名操作は代表者のみ可能。
  1. ユーザがチーム名を検索。
  2. チーム代表者に参加リクエストを送信。
  3. 代表者が承認後チームに参加可能

* チーム所属人数上限：上限なし
